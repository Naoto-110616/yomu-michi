# 読む道 / yomu-michi

**本と本のあいだを地図にする。**

「この本を読む前に、何を読んでおけばいいのか」——歴史や科学の本を読むときに毎回ぶつかるこの問いに、
線で答えるための地図です。1002冊を **前提 / 発展 / 別視点 / 反論** の4種類の関係でつないでいます。

▶ **https://naoto-110616.github.io/yomu-michi/**

---

## なぜ「関係」を単位にしたか

既存の読書サービス（ブクログ、読書メーター、StoryGraph など）はすべて **ノード型** です。
1冊について感想を書く。この形式は完成しきっていて、しかも重い。

一方、論文の世界には Connected Papers や ResearchRabbit のような **関係のネットワーク** を見るサービスが揃っています。
論文には「引用」という明示的なエッジが最初からデータとして存在するからです。書籍にはそれがない。
だから誰も作っていない——これが出発点です。

このリポジトリは、その欠けているエッジを

1. 賞・ランキングから **自動生成できる分** を機械で作り
2. 自動生成では作れない分を **人が張る**

という二層構造で埋めようとしています。

## 分かったこと：自動生成できるのは「別視点」だけ

| 関係 | 本数 | 生成方法 |
|---|---:|---|
| 別視点 (alt) | 1383 | 自動 — 同じ賞の同年ノミネート、同一著者、同じランキング内 |
| 前提 (pre) | 24 | **ほぼ人手** |
| 発展 (next) | 19 | 自動（シリーズ判定）＋人手 |
| 反論 (counter) | 5 | **人手のみ** |

開発の途中で「同じリスト内で年代が前の本を前提とみなす」規則を書いたところ、
`博士の愛した数式 → 村上海賊の娘（本屋大賞の系譜）` のような**無意味な線が大量に生成された**ため、
すべて `alt` に降格しました。

**前提と反論は、機械には作れません。** これが最大の発見であり、
このプロジェクトの次のフェーズ（投稿できるSNS化）の根拠になっています。
Atlas の「人が張った線だけ」モードを見ると、1000冊の海に29本しか線が残りません。
その疎さが、そのまま人間の投稿で埋めるべき空白です。

## データの集め方

1冊ずつ探すのは効率が最悪なので、**賞とランキングをリスト単位で丸ごと**取っています。
重要なのは、リストが **ノードの供給源であると同時にエッジの供給源でもある**こと。
同じ賞の同じ年にノミネートされた作品同士は、それだけで「同時代の別視点」になります。

収集元：本屋大賞（2004–2026）/ 直木賞 / 芥川賞 / このミステリーがすごい! / 本格ミステリ大賞 /
日本SF大賞 / 星雲賞 / ヒューゴー賞 / ネビュラ賞 / ブッカー賞 / ピューリッツァー賞 / ノーベル文学賞 /
NHK「100分de名著」全放送回 / 紀伊國屋じんぶん大賞 / 新書大賞 / ビジネス書大賞 / 講談社科学出版賞 ほか

生データ 1046 件 → 表記ゆれ吸収・副題除去で **1002 ノード / 1431 エッジ**。

## 構成

```
app/                 Next.js App Router（静的書き出し）
components/
  Atlas.tsx          canvas + パン/ズーム/選択。React state と ref を draw() 時に合成する
  Controls.tsx       モード・関係種別・領域・検索
  DetailPanel.tsx    選択した本の「向かっている線 / 伸びている線」を理由つきで表示
lib/
  graph.ts           ドメインモデル（RelationType が中心）
  render.ts          Canvas 描画・ヒットテスト・ラベル衝突回避
data/graph.json      Web が読む圧縮済みグラフ（派生物。gitignore 済み）
pipeline/
  build.py           マージ・正規化・エッジ生成・力学レイアウト（座標をここで確定させる）
  pack.py            文字列を辞書化して 389KB → 131KB に圧縮
  shelf.py           所有者の本棚93冊（★評価つき）
  sources/*.json     賞・ランキングの生データ（これが真のソース）
```

レイアウトは **Python 側で確定**させて座標ごと配信しています。
ブラウザで毎回シミュレーションを回さないので 1000 ノードでもスマホで軽く、
かつ**毎回同じ形**になる——「地図」として扱うならこちらが正しい。
乱数はシード固定なので、CI で何度ビルドしても 1 バイトも変わりません。

## 開発

```bash
npm install
pip install numpy    # レイアウト計算に使う

npm run data         # pipeline/sources → data/graph.json を生成（初回に必須）
npm run dev          # http://localhost:3000
```

`data/graph.json` は派生物なのでリポジトリに入っていません。`npm run data` で作ります。

本を追加したいときは `pipeline/sources/` に
`[{"t":"タイトル","a":"著者","y":2020,"src":"出典ラベル","cat":"sf"}, ...]`
形式の JSON を置いて `npm run data` を実行してください。
`src` が同じ本どうしは自動でリング状に接続されます。

前提・反論の線は `pipeline/build.py` の `SEED` に手で書きます。ここは今のところ人間の仕事です。

## デプロイ

`main` に push すると GitHub Actions が

1. `pip install numpy` → `npm run data`（グラフ生成）
2. `npm run build`（`output: 'export'` で静的書き出し）
3. `gh-pages` ブランチへ配信

まで自動で行います。初回だけ Settings → Pages で Source を `gh-pages` に指定してください。

Vercel など別のホストに移す場合は、リポジトリを Import して
`NEXT_PUBLIC_BASE_PATH` を設定しない（＝ルート配信）だけで動きます。
Build Command に `pip install numpy && npm run data && npm run build` を指定してください。
